## 1 项目概述

### 1.1 背景

2026 年 11 月，Stillframe（定格）以 MIT 协议开源：网页端通过 GitHub Pages 上线，桌面端（Tauri 2）与 Android 端（WebView 加 MediaProjection）源码同仓维护，三条 GitHub Actions 流水线（网页构建、桌面 cargo check、Android assembleDebug）均已通过。

首版的界面规格不是自行设计，而是从本机 QQ 9.9.38（QQNT）的 QQScreenShot 资源包逐项读出：工具栏 15 个按钮的顺序、12 色调色板的色值、三档线宽、12 款滤镜名称、132×152 放大镜、459×40 长截图条、录屏条六件套、540×440 识图与翻译窗、600×500 贴图窗，以及一批中文提示语。规格与证据记录在 docs/QQ-PARITY.md，提取脚本为 tools/qq-resource-probe.py。

功能骨架已经成立，但与 QQ 的实际行为仍有可量化差距，集中在录制管线、长截图自动化、保存落盘与移动端细节。本项目书给出下一阶段的升级范围、技术路线、排期与验收口径。

### 1.2 目标

第一，行为对齐。以 QQ 9.9.38 为唯一行为基准，逐项覆盖九个能力域；任何未对齐项必须写进 docs/QQ-PARITY.md 的差异表，不允许用描述性文字替代实现。

第二，三端一致。同一套界面与数据模型跑在网页、桌面、Android 三个容器中，能力差异以矩阵方式声明；平台做不到的部分由原生壳补齐，而不是在文档里假设它已经做到。

第三，可交付。v1.0 发布正式 Release，包含网页静态包、Windows 安装包与 Android APK；文档、测试、CI 与许可证齐全，外部开发者拿到仓库一小时内能跑起来。

### 1.3 范围

本次升级覆盖九个能力域：区域截图与放大镜、标注编辑、滤镜、滚动长截图、区域录屏、屏幕识图、屏幕翻译、贴图钉屏、会话与落盘（自动保存、图库、隐藏当前窗口、全局热键）。

### 1.4 非目标

不复制、反编译或再分发 QQ 的任何二进制、图片、字体与私有协议；不做云端同步与账号体系；不做 iOS 系统级抓屏；不内置任何按次计费的翻译或 OCR 云服务；不以像素级复刻 QQ 皮肤为目标，只对齐布局、顺序、文案与交互结果。

### 2.4 结论

界面层已经完成对标，缺的是行为层与平台层。下一阶段不再新增视觉元素，把预算集中在三件事：把自动化做实、把原生能力接满、把质量与发布补齐。

## 3 总体升级方案

### 3.1 原则

先框架后填充：每个能力先落最小可用链路，再补细节，避免半成品堆叠。可以弱但不能没有：任何能力至少保留入口与可用降级路径。不以硬件裁剪功能：性能问题用分块渲染、降采样与原生管线解决，而不是删掉功能。

### 3.2 分层架构

现有代码分为六层：宿主适配（src/lib/desktop.ts）、抓屏（capture.ts）、图像处理（annotate.ts、filters.ts、stitch.ts、image.ts）、录制（recorder.ts）、面板（components/panels）、持久化（storage.ts、autosave.ts、settings.ts）。

升级新增一层处理管线 pipeline：把“抓到的帧或图像”到“可交付结果”之间的步骤显式化，包括解码、裁剪、滤镜、标注、编码、落盘。管线以纯函数与可测试模块实现，面板只负责交互。这样录制、长截图与截图导出共用同一条链路，避免三套重复逻辑。

### 3.3 技术选型

**表4 升级涉及的技术选型**

| 领域 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 18、Vite 5、TypeScript 5.6（沿用） | 现有代码与 CI 稳定，迁移成本为零 |
| 桌面壳 | Tauri 2 加 xcap 抓屏、global-shortcut（沿用） | 体积小，系统级能力够用 |
| 录制编码 | xcap 连续抓帧，FFmpeg sidecar 编码 | 绕开 WebView 的 MediaRecorder 限制，直出 MP4 |
| 滤镜 | OffscreenCanvas 加 WebGL LUT，Canvas filter 兜底 | 导出保真，预览可降采样 |
| 文字识别 | tesseract.js 本地识别（沿用） | 不上传图片，隐私可控 |
| 翻译 | OpenAI 兼容、DeepL、LibreTranslate 三适配（沿用） | 用户自选出口，不绑定供应商 |
| 测试 | Vitest 加 Playwright | 与现有构建链一致，CI 可直接跑 |
| 发布 | GitHub Actions 加 Pages 加 Release | 与现有仓库流程一致 |

### 3.4 兼容策略

网页端保留全部能力的降级入口：抓屏依赖用户授权，自动保存依赖 File System Access，贴图仅页面内浮层并明确标注不能置顶。桌面端与 Android 端通过宿主桥补齐系统能力，宿主缺失时回落到网页实现并在界面上说明，不允许静默失败。

- 交付物：`desktop/src/recorder.rs`（FFmpeg 编码器 + `crop_rgba`）、`start_recording` / `stop_recording` 两条命令、前端桌面分支（`nativeStartRecording` / `nativeStopRecording`，`RecordPanel` 原生走 30 帧并显示 `秒 · fps · 帧数`）、README / CHANGELOG / ARCHITECTURE 同步。

- 已验（Linux）：90 帧合成画面 → `ffprobe` 核对 h264 / 320×240 / `nb_frames=90` / `duration=3.000000`，裁剪长度与预期一致。

**v0.3 录制第二批：Windows 真机达标 + DXGI 抓帧（2026-11-27）**

先把「抓帧慢」这条根因挖到底，再谈帧率。真机（i5-8250U / 1920×1080 / 远程会话）逐层实测：

| 环节 | 手段 | 实测 | 结论 |
| --- | --- | --- | --- |
| 抓帧 | `xcap::capture_image()` | 236 帧/59.81s = **3.9fps** | 封装开销，弃用 |
| 抓帧 | 自建 `BitBlt` + `CreateDIBSection`（零拷贝） | 1506 帧/60.03s = **25.1fps**，抓帧 38ms | 单帧成本高，且随机 40–56ms 漂移 |
| 抓帧 | DXGI Desktop Duplication（`CopyResource` → staging → `Map`） | 抓帧 **6–9ms** | 走合成器，成本降一个数量级 |
| 编码 | libx264 `veryfast` | 写入阻塞 28ms，帧率掉到 15.4fps | 编码成为第二瓶颈 |
| 编码 | libx264 `ultrafast` | 60 秒 1506 帧 = 25.1fps，写入 1.7ms | 软件编码勉强够 |
| 编码 | `h264_qsv`（核显，先真编 5 帧探测驱动可用性） | 写入 **1.4–3.2ms** | CPU 让给抓帧，达标关键 |

最终成片数据（全部 `--record-probe` 真机实测，ffprobe 核对）：

| 场景 | 帧数 | 成片时长 | 内容帧率 | 丢帧 | 抓帧 / 写入 | 后端 |
| --- | --- | --- | --- | --- | --- | --- |
| 1920×1080 / 60 秒 | 1800 | 60.000000 | 29.0fps | 0.44% | 6.1 / 1.7ms | dxgi+h264_qsv |
| 1920×1080 / 60 秒（复测） | 1800 | 60.000000 | 27.9fps | 0.72% | 9.4 / 2.8ms | dxgi+h264_qsv |
| 1280×720 / 40 秒 | 1200 | 40.000000 | 28.1fps | 0.75% | 9.3 / 1.4ms | dxgi+h264_qsv |

- **指标结论**：1080p×60 秒三轮均值 28.3fps、丢帧均 <1%，达到「≥28fps、丢帧 <2%」。输出恒为 30fps CFR，`fps` 报的是内容更新率（静止时 DXGI 不给新帧，用上一帧顶住时间轴）。
- 其余关键修复：`timeBeginPeriod(1)`（Windows 默认定时器粒度 15.6ms 会把 `sleep(33ms)` 拉成 46ms）；落后节拍时重复帧补时间轴 + 收尾 `pad_to`，否则慢于目标帧率时成片会快放（修前实测 60 秒录成 47 秒）；`SelectObject` 句柄失效自动重建，锁屏 / 远程重连不再断录。
- 回退链：DXGI 建不起来（旧卡 / 会话不支持 / 驱动拒绝）自动退 `BitBlt`，`h264_qsv` 不可用自动退 `libx264`，两条都在 `backend` 字段里可查（如 `gdi+libx264`）。
- 仍未做：FFmpeg sidecar 随包分发、4K 内存峰值与脏矩形优化。声音链路已在第四、五批接通（麦克风独立进程 + WASAPI 环回，两路可同时），录屏标注在第六批逐帧合成进成片。
- 旁证：本机 `tools/recorder-check`（CI 同款断言）跑通——`codec_name=h264 / 320x240 / nb_frames=90 / duration=3.000000`，说明编码链在改动后仍可脱离 GUI 复验。

**v0.3 录制第六批：录屏标注进成片（2026-11-27）**

- 交付物：`desktop/src/win_annot.rs`（DIB 离屏画布 + GDI 绘制 + `has_activity` / `draw` / `pixels`）、`lib.rs` 的标注快照槽与三条命令（`push_record_annotation` / `push_record_laser` / `undo_record_annotation` / `clear_record_annotation`）、`record_loop` 每帧合成、`--probe-annot=<json>` 标定入口、前端 `toNativeAnnotation()` + `RecordPanel` 推送。

## 5 关键技术方案

### 5.1 自动滚动长截图

问题：QQ 的自动滚动不是简单连拍，而是按方向驱动目标窗口滚动固定距离，再判断是否已经到底。当前实现只有按钮，没有驱动与判定。

方案：驱动层按平台分三条实现。Windows 使用 SendInput 注入滚轮事件，滚动量取视口高度的 70%，避免整屏跳变导致重叠区不足；macOS 使用 CGEvent 创建滚轮事件；Android 在应用内滚动场景用无障碍手势，系统级滚动不承诺。判定层沿用现有行亮度签名，但把比对范围从全宽改为左右各留 8% 边距，降低滚动条与装饰条的干扰；连续两次找不到重叠且画面差异低于阈值时判定到底，立即停止并回退到手动追加模式。

验收：20 屏列表页一次采集完成，拼接结果无明显断层；驱动失败时不静默，界面提示改用手动模式。

### 5.2 桌面录制管线

问题：WebView 内的 MediaRecorder 只能输出 WebM，而桌面壳逐帧拉取屏幕的速率只有个位数，两者都不满足“可交付录像”。

方案：抓帧线程以 30 帧为目标循环调用 xcap，写入三帧环形缓冲；编码进程由 FFmpeg sidecar 承担，rawvideo 格式从标准输入读入，libx264 veryfast、CRF 20，音频由 WASAPI 环回采集系统声、与麦克风在 48kHz 立体声下混合。首帧到达后才启动编码，避免片头空白；掉帧计数写入日志并在结束页展示实际帧率。标注层仍在 canvas 合成，保证箭头、文字与激光进入成片。

> **实施修订（2026-11-27 录制第二批实际做法）**：抓帧不再用 xcap——`capture_image()` 真机 3.9fps，封装开销占大头。改为 `FrameGrabber`：优先 DXGI Desktop Duplication（6–9ms/帧），回退 BitBlt（25fps 量级）；编码先探测 `h264_qsv` 用核显，回退 libx264 ultrafast；不做「三帧环形缓冲」，改为按节拍直写管道 + 落后时重复帧补齐 + 收尾 `pad_to`，保证成片时长等于录制时长。实测见 §4.2「录制第二批」表。
>
> **音频落地（2026-11-27 录制第三批）**：麦克风已接通。做法比原方案再退一步——**音频不接进编码器，单独起一个 FFmpeg 进程录 48kHz 单声道 WAV**，停录时发 `q` 让它正常收尾，再用两段有限文件封装（`-c:v copy -c:a aac`）。原因是把 dshow 当编码器的第二输入时，它是无限实时流：视频 stdin 已 EOF，FFmpeg 仍在等音频，`-shortest` 也不生效，实测停录后进程不退出，界面会卡死。
>
> 起点对齐用自动校准：WAV 是 48kHz/16 位，按字节数就能算出它录了多久，比画面多出来的那段用 `-ss` 裁掉，尾部再 `-shortest` 追齐，两头都关上。实测 1080p/30 秒带麦克风成片 29.933 秒、音频 29.999 秒，音画差 66ms；15 秒样本差 32ms。
>
> 顺带修掉三个时长问题：① 统计秒数原先在补帧和等 FFmpeg 之后才取，20 秒录成 43 秒——改为录制线程停下即 `mark_end()` 钉住；② 补帧用「节拍累加器」会补超前，15 秒录出 466 帧——改为「已跑秒数 × 帧率」绝对对账；③ `sleep(3ms)` 在 Windows 上常常只睡 1–2ms，每帧欠一点、帧率偏高——改为剩 2ms 以内忙等到点。修完无麦克风 60 秒回到 1800 帧 / duration 60.000000。
>
> **系统声落地（2026-11-27 录制第五批）**：原文里「WASAPI 环回」这一句是真的，但要自己做——实测 `ffmpeg -hide_banner -devices` 只有 `dshow` / `openal`，`-f wasapi` 报 `Unknown input format`，dshow 侧也没有立体声混音端点。于是新增 `desktop/src/win_audio.rs`：默认渲染端点 → `IAudioClient::Initialize(AUDCLNT_STREAMFLAGS_LOOPBACK)` → `IAudioCaptureClient` 逐包读，按 `GetMixFormat()` 的真实格式（44.1k/48k、多声道、32 位浮点）混成单声道 i16 WAV，停止时回填 RIFF 头。
>
> 多源封装：`EncoderSpec` 带 `system_audio`，收尾时按 0/1/2 条音轨分流——1 条直接 map，2 条（麦克风 + 系统声）`amix=inputs=2:duration=longest` 合成一条 AAC；每条都按自己的 WAV 头算时长裁头，尾部 `-shortest` 追齐。WAV 不足 2KB 视为没采到，直接删掉，不给成片塞空音轨。
>
> 真机：720p×20 秒 + 系统声（同放 440Hz 正弦）→ `dxgi+h264_qsv+sys`、600 帧 / 20.01 秒 / 28.8fps、音轨 19.816 秒、`mean_volume -5.0 dB`；两路同开 → `dxgi+h264_qsv+mic+sys`、450 帧 / 15.000000 秒、单条 AAC 705 帧。全程无播放时成片无音轨、画面照常完整。
>
> 边界写进 README：环回采的是默认播放设备的渲染内容，录制期间没播就没音轨；远程/无播放设备的会话要按这个前提验收。
>
> **标注进成片落地（2026-11-27 录制第六批）**：原方案「标注层仍在 canvas 合成」对桌面壳不成立——桌面端的帧根本不进 canvas，WebView 里那套绘制碰不到 Rust 的抓帧缓冲。于是反过来：**前端只推事件，后端逐帧烧**。新增 `desktop/src/win_annot.rs`，抓帧器交出的 BGRA 直接拷进一块 32 位 top-down DIB，再用 GDI 画矩形（5 点闭合折线）、椭圆（48 边形）、箭头（线 + 实心三角）、文字（`Microsoft YaHei UI` + `TextOutW`，行距 1.28）、激光（随时间收缩的红点，1.2 秒残影）。
>
> 坐标、线宽、字号全部由前端按选区归一化到 `0..1`，后端按帧尺寸乘回来，DPI 与非整数缩放都不用额外换算；`atMs` 以开始录制为原点。前端在标注落定即推（`push_record_annotation`）、激光按 40ms 节流推（`push_record_laser`），撤销 / 清除各有命令同步到后端，只影响后续帧。
>
> 零成本跳过：一条活动标注都没有的帧不碰 DIB，直接喂原始缓冲。真机 1280×720×12 秒 5 条标注 → 360 帧 / 12.000 秒 / 丢帧 0，`write_avg_ms` 2.3 → 3.8（每帧多 1.5ms），抽帧核对 1s/2s/3s/4s/5s 五条按序出现。验收手段是 `--probe-annot=<json>` 预置标注。
>
> 取舍：GDI 无抗锯齿、标注不可再选中拖拽。要更细腻需换 Direct2D/Skia 后端，列为后续项。


验收：1080p 连续 60 秒，实测帧率不低于 28，成片在系统播放器中正常播放，音画偏差小于 100 毫秒。

### 5.3 滤镜

问题：现有实现用 Canvas filter 调色，十二款滤镜的层次与暗角不统一，观感与 QQ 差距明显。

方案：为十二款滤镜各生成一组 3D LUT 或颜色矩阵加曲线参数，预览阶段把图像降采样到长边不超过 1280 像素再套 LUT，导出阶段按原分辨率渲染；WebGL 不可用时回退现有 Canvas 实现，并在设置页标注当前为回退模式。

验收：导出图与预览图色彩一致，十二款滤镜在同一张测试图上差异可辨，切换耗时低于 200 毫秒。

### 5.4 识图与翻译版面

问题：tesseract 只给出带坐标的词块，现有代码按行拼接成纯文本，段落关系丢失；翻译结果整段替换，无法对照原文。

方案：识别结果按 hOCR 坐标做段落聚类，行间距超过 1.6 倍行高视为新段落，段内按坐标排序并修正全半角标点；编辑区保留段落结构，复制与导出都按段落输出。翻译面板改为双栏，左右同步滚动，支持导入 JSON 术语表，provider 超时 8 秒后降级为原文并在状态栏提示。

验收：三页中英混排文档段落还原正确率不低于 85%；双栏滚动不脱节；术语命中率可复核。

> **实施修订（2026-11-27 取字第七批）**：段落聚类已落地（`groupParagraphs`：行距 >1.4 倍中位行高、左边界跳变、跨列强制断段），编辑区有「行视图 / 段落视图」切换。原方案里「导出按段落输出」落成 `src/lib/markdown.ts` 的 `paragraphsToMarkdown`：清单补 `-`、代码包块、正文段间空行，面板加「导出 Markdown」。**未采用「转为某家在线文档」**——开源工具不绑在线服务，给 Markdown 即可粘进任何文档；「表格转真表格」也没做，识别结果没有列分隔符，硬猜会错行，改为按行保真。
>
> 未验：段落还原率 85% 这一项还没对真图做量化（现有只是定性观察：整窗 1938×1048 → 2041 字符 / 7 段 / 置信度 75）。

> **实施修订（2026-11-27 取字第八批：量化 + 多栏切栏）**
>
> **量化落地**：`tools/ocr-bench/` 用 PIL 画七张版面（中文 / 中英混排 / 清单+代码 / 双栏窄距 / 双栏宽距 / 13px 小字 / 深色），真值与图同脚本生成，`bench.mjs` 复现线上管线（`toOcrBlob` 缩放 → 900 宽找栏 → 逐栏识别 → 聚段）后与真值对齐。实跑：还原率 **99.6%**、段落纯度 **99.5%**、整段正确 **30/30**，七页全过 85% 线。结果存 `report.json`，判定条件写进 `tools/ocr-bench/README.md`。
>
> **指标为什么是两个**：只算 recall（真值段能否找到一段对得上）时，两段被并成一段仍然满分——这个错法在基准里真的出现过（双栏页 recall 99.3%、纯度却只有 85.1%）。所以补了 purity（每个 OCR 段多纯）反向卡一次，两条都过 85% 才算过。
>
> **由量化暴露的两处修正**：① 段距 34px 且上一段恰好满行时，两段间隙不到 1.4 倍中位行高会被并段——断段阈值收窄到 1.25 倍，段首缩进信号从 2.2 倍收到 1.8 倍；② 双栏截图在**行级**就被 tesseract 拼成一条 line（`机柜重新整理…图纸上。 = - 上行端口 24个`），段级无法挽回，只能在识别前按竖向空白切栏：新增 `src/lib/columns.ts`（逐列数墨，只认内部切口、每栏 ≥18% 宽、最多 3 栏），`recognize()` 多栏时逐栏裁切识别再拼回坐标；切栏后双栏页纯度 85.1% → 100%（3 段 → 4 段）。
>
> **仍未覆盖**：七页是干净合成图（字号统一、无 JPEG 噪声、无缩放糊字），只能证明管线逻辑对；带噪声的真实截图样本待补。栏间没有可见竖向空白的版面（仅靠细线或底色区分侧边栏）切不开，仍会串行——这条已写进 README 已知限制。


### 5.5 贴图与隐藏窗口

问题：贴图只有单窗，缩放不保比例，没有数量上限；隐藏自身窗口依赖前端主动调用，异常时主窗可能一直不可见。

方案：贴图改为窗口集合管理，记录 id、位置、缩放与层级，角柄拖拽保持原始宽高比，滚轮缩放以指针为中心，超过 20 张按 QQ 文案提示；关闭统一走窗口销毁并清理记录。隐藏窗口改为“先隐藏、再抓屏、成功或失败都恢复”的三段式，恢复放在 finally 分支，并在 800 毫秒后强制兜底显示。

验收：连续开满 20 张贴图不崩；截图失败时主窗 1 秒内恢复可见。

### 5.6 移动端

问题：Android 侧已接通 MediaProjection 与悬浮窗，但选区是整屏，贴图权限申请与分享链路不完整。

方案：用 VirtualDisplay 加 ImageReader 取帧，前台服务常驻通知；选区改为拖拽加放大镜，松手后进入标注台；贴图使用 TYPE_APPLICATION_OVERLAY，首次申请权限时给出用途说明；导出后通过 FileProvider 分享到聊天与相册应用，避免直接写公共目录。

验收：Android 12 与 14 各完成一次截图、一次录屏、一次贴图与一次分享。

### 5.7 性能与内存

问题：4K 截图会在底图、滤镜副本、导出画布上各留一份全尺寸位图，内存峰值不可控。

方案：底图与标注层分离，标注层只重绘脏矩形；滤镜预览降采样，导出时才全尺寸渲染；长图按段拼接，最后一次性合成；帧数据用 ImageBitmap 传递，及时释放中间画布。

验收：4K 截图内存峰值不超过 400MB，1080p 场景不超过 250MB；20 屏拼接总耗时不超过 3 秒。

## 7 风险与对策

**表12 主要风险与对策**

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
| 系统权限受限（macOS 录屏授权、Android 前台服务） | 高 | 核心能力不可用 | 首次使用给出权限引导页；失败即说明原因，不假装成功 |
| FFmpeg sidecar 体积与许可 | 中 | 安装包变大，许可需合规 | 使用 LGPL 构建，随包附许可文本，安装包控制在 40MB 内 |
| 与 QQ 界面相似引发商标与不正当竞争争议 | 中 | 仓库被投诉或下架 | 不复制任何资源与代码；文档明确功能对标关系；不使用其图标与字体 |
| 性能不达基线（本机 7.4GB 内存、无独显） | 中 | 体验回落 | 预览降采样、分块渲染；录制默认 1080p，4K 需显式开启 |
| 范围膨胀导致版本延期 | 高 | 发布推迟 | 每个版本只认退出条件；未达标项移入下一版本并写进文档 |

## 9 开源治理

分支策略：master 保持可发布，功能走短分支加 PR，合并前必须通过网页、桌面、Android 三条 CI。版本号遵循语义化版本，破坏性变更写进 Release 说明。

发布产物：网页静态包随 Pages 自动部署；桌面安装包与 Android APK 通过 Release 附件分发，附校验和；每次发布同步更新 README 的能力矩阵与已知限制。
